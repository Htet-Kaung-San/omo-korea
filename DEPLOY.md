# Deploying Hey! PNU

Two services on [Render](https://render.com): a Node API and a static site.
`render.yaml` in the repo root defines both, so Render can create them together.

The reason to host this at all is that **the API keys stay on the server**.
Nobody needs a copy of `backend/.env` to use the assistant — they just open the
site. Every secret is entered once in the Render dashboard and never written to
this repo.

---

## 1. Create the services

1. Push this branch to `main`.
2. On Render: **New → Blueprint**, pick this repository, apply.
3. Render reads `render.yaml`, creates `heypnu-api` and `heypnu-web`, and asks
   for the values below.

`JWT_SECRET` is generated by Render — do not paste one. Everything else comes
from your `backend/.env`.

### `heypnu-api`

| Variable | Where it comes from |
|---|---|
| `SUPABASE_URL`, `SUPABASE_KEY`, `SUPABASE_SECRET_KEY` | `backend/.env` |
| `OPENROUTER_API_KEY`, `OPENROUTER_MODEL` | `backend/.env` |
| `GEMINI_API_KEY` | `backend/.env` |
| `RESEND_API_KEY`, `RESEND_FROM_EMAIL` | `backend/.env` |
| `CORS_ORIGINS` | the site URL — fill in after step 2 |
| `APP_BASE_URL` | same as `CORS_ORIGINS` |

### `heypnu-web`

| Variable | Value |
|---|---|
| `VITE_API_BASE_URL` | the API URL **plus `/api`** — fill in after step 2 |
| `VITE_NAVER_MAP_CLIENT_ID` | `backend/.env` (safe to expose; it is domain-locked) |

---

## 2. Point the two at each other

Render assigns URLs on first deploy, so these three can only be filled in once
both services exist. Assuming `heypnu-api.onrender.com` and
`heypnu-web.onrender.com`:

```
# on heypnu-api
CORS_ORIGINS   = https://heypnu-web.onrender.com
APP_BASE_URL   = https://heypnu-web.onrender.com

# on heypnu-web
VITE_API_BASE_URL = https://heypnu-api.onrender.com/api
```

Then redeploy both.

Three things that will silently break if they are wrong:

- **No trailing slash on `CORS_ORIGINS`.** `index.js` compares
  `req.headers.origin` against the list literally, so
  `https://heypnu-web.onrender.com/` never matches and every request is
  blocked by the browser.
- **`VITE_API_BASE_URL` must end in `/api`.** The client appends paths like
  `/students/feedback` straight onto it. Getting this wrong gives 404s on
  every call, not an obvious error.
- **`VITE_` variables are baked in at build time.** Changing one requires a
  rebuild, not a restart.

---

## 3. Sanity check

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://heypnu-api.onrender.com/api/students/courses
```

`200` means the API is up and reaching Supabase. Then open the site, sign in,
and ask the assistant something — that exercises the whole chain: auth, RAG
retrieval, the model, and SSE streaming.

---

## Two things worth knowing

**The free plan sleeps.** A free Render service spins down after ~15 minutes
idle, and the next request waits roughly 50 seconds for a cold start. Fine for
teammates trying the assistant; not what you want thirty seconds before a demo.
Open the site a few minutes beforehand, or upgrade that one service for the day.

**The community feed will be empty.** This is deliberate. The feed queries
Postgres directly from the browser using `VITE_SUPABASE_ANON_KEY`, and Vite
inlines every `VITE_` variable into the JavaScript it ships — so setting it
would publish a working database credential, and only `student_timetable` and
the course tables have row level security. A logged-in student could read and
write every other table, including making themselves an admin.

So the blueprint deliberately omits it, and `frontend/src/lib/supabase.ts`
returns `null` without it, which makes the feed return `[]`.

The fix is not to set the key. The Express endpoints already exist
(`GET`/`POST /api/students/community/posts`, plus like and delete) and
`api.getCommunityPosts` is already written and unused — the feed needs to be
moved onto them. That loses realtime push and gains a browser bundle with no
credentials in it. Roughly an hour of work; worth doing before anyone shares
the URL widely.
